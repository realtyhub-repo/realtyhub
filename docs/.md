## Notas

1. **`PasswordResetToken` y `EmailVerificationToken` son estructuralmente idénticas** (id, user_id, token_hash, expires_at, used, created_at). Se mantienen separadas por ahora para mayor claridad; más adelante se podría evaluar fusionarlas en una tabla genérica `verification_token` con una columna `tipo` si se quiere reducir duplicación.

2. **`TokenGenerator` se reutiliza en tres flujos distintos** (refresh token, verificación de email, reset de password) — es el mismo patrón de "generar aleatorio + hashear" en los tres casos, por eso vive como un componente independiente en vez de estar acoplado solo a `RefreshTokenService`.

3. **Orden de implementación recomendado:**
    - Login local (`register` + `login`) con bloqueo de proveedor duplicado — lo mínimo pedido por el profesor.
    - Verificar que funcione junto con el login de Google ya existente.
    - Verificación de email.
    - Recuperación de contraseña (al final, reutilizando el patrón de token ya probado).

4. **`AuthProvider` actualizada** — `google_id` y `password_hash` ahora son `nullable`, y se agregó la columna `email` (única) para poder validar el bloqueo de proveedor duplicado sin depender de una llamada a User Service en cada registro/login.
